# Per-Channel allow-listed inbound header forwarding

`processDelivery` forwards only the Channel's `forwardHeaders` allow-list of inbound header names (matched case-insensitively against the Broadcast's stored headers, ADR 0002) — empty by default, so every existing Channel's delivery is unchanged. Forwarded headers are merged into the outbound request before the operator-configured `endpoint.headers`, so an explicit Endpoint header always wins a name collision; `content-type` still comes from the Broadcast last, as before. `authorization` is never forwarded, even if named on the allow-list — that header carries the Channel's own ingest token, and forwarding it would turn a read-only fan-out subscription into write access on the Channel for every Endpoint. Rejected at configuration time (`channelCreateSchema`/`channelUpdateSchema`) and re-checked at delivery time as a backstop. This is deliberately "forward the named few", never "forward all": the same inbound request the sender's credential rides in also carries that ingest token.

The allow-list selects from what ADR 0002 **already persisted**, so it is bounded by the ingest header filter and cannot widen it: `DEFAULT_INGEST_HEADER_DENYLIST` (`apps/api/src/ingest/headers.ts`) drops `authorization`, `cookie`, `set-cookie`, `proxy-authorization`, `x-api-key`, and `x-auth-token` before the Broadcast is written, and `mergeIngestHeaderDenylist` re-unions those defaults so no env setting can opt out. Naming one of them in `forwardHeaders` is therefore accepted at configuration time but forwards nothing — the header was never stored. That is deliberate for `authorization`, but it also means a sender credential presented as `x-api-key` or `x-auth-token` cannot be relayed at all, which is the motivating case in issue #37. Widening the ingest filter (globally or per-Channel) is a change to ADR 0002's storage posture, not to this decision, and is left open. Header names are otherwise unvalidated beyond "non-empty, not `authorization`", so naming a connection-scoped header (`host`, `content-length`, `transfer-encoding`) would inject it into the outbound request; nothing forwards by default, so this stays an operator-configuration concern rather than a delivery-path guard.
