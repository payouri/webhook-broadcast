# Expand/contract migration discipline

ADR 0008 says migrations "always follow expand/contract" and that `drizzle-kit migrate` runs in a `migrate` service/job that `depends_on: service_completed_successfully` before `api`/`worker` start. That's the deploy-ordering half of the story — compose guarantees the *new* migrations are applied before *new* code runs, but it says nothing about the *old* code and *old* rows that are still live during a rolling deploy, or about how a Drizzle migration in this repo should be shaped so that guarantee is actually safe to rely on. This addendum is the checklist: how a schema change here goes from additive to complete without a window where old code, new code, old rows, or new rows can see a shape they don't understand.

Every migration in `packages/db/migrations` is a plain, already-applied SQL file generated by `drizzle-kit generate` from `packages/db/src/schema.ts` and replayed in order by `drizzle-kit migrate` / `runMigrations()` (`packages/db/src/migrate.ts`) — there is no down-migration and no in-place edit of a shipped file. Because compose's `migrate` job runs once, ahead of both `api` and `worker`, and because a rolling deploy briefly runs old and new application code against the *same* already-migrated database, a breaking change split across "add" and "drop" in one revision is unsafe: the old code is still querying the shape the drop just removed. Splitting the same change into two independently-deployable revisions removes that window entirely.

## The checklist

1. **Expand** (migration N): add-only — a new nullable/defaulted column, a new table, a new index. Never rename or drop in this revision. Backfill existing rows in the same migration when it's cheap and safe (a single `UPDATE ... WHERE new IS NULL`); for a large table, backfill in a follow-up batch job instead so the migration itself stays fast and lock-light. Mind the locks: `runMigrations()` applies each file inside one transaction, so `CREATE INDEX CONCURRENTLY` is not available here — a plain `CREATE INDEX` holds a `SHARE` lock that blocks writes to the table for the whole build, and an in-migration `UPDATE` holds row locks for the whole sweep. Both are fine on a table of this size and both need an out-of-band plan once it isn't. Land and deploy this alone — nothing in application code has to change yet, and nothing does.
2. **Dual-write / dual-read** (a later, separate deploy — no new migration): application code starts writing the new shape (and, for a rename, still writing the old one too) and reading the new shape with a fallback to the old. This is an ordinary code change, reviewed and shipped like any other; it depends on migration N already having run everywhere, which compose's `migrate`-before-`api`/`worker` ordering already guarantees.
3. **Backfill & verify** (only meaningful _after_ step 2 is live everywhere): step 1's backfill covered the rows that existed when migration N ran, and step 2's dual-write covers rows written from then on — but neither covers the rows written **between** the two deploys, by code that only knew the old shape. That gap is the whole reason this step exists and it does not close on its own: re-run the sweep (`UPDATE ... WHERE new IS NULL`, batched if the table is large) once every replica is dual-writing, so no fresh NULLs can appear behind it. Then verify: the sweep's residual count is zero, and reads no longer take the fallback path in practice — e.g. by grepping logs/metrics for the fallback branch, or a one-off count query.
4. **Contract** (migration N+1, its own revision, only after step 3 holds for every replica and every in-flight deploy of old code has rolled off): drop the old column/table/index and any dual-write code that referenced it. This is the only revision allowed to contain a destructive `DROP`/`ALTER ... DROP COLUMN`, and it must not be bundled with any new "add."

Each phase ships as its own deploy. A migration file that mixes an add a caller needs with a drop in the same revision fails step 1 — that is the anti-pattern this checklist exists to rule out.

## Worked example: `attempt.n` → `attempt.attempt_number`

`attempt.n` (the DB column) has been a single, cryptic letter since the initial schema (ADR 0007) even though application code already calls the same value `attemptNumber` (see `apps/api/src/worker/processDeliveryJob.ts`). Migration `0006_curious_thena.sql` is the **expand** step of renaming it:

```sql
ALTER TABLE "attempt" ADD COLUMN "attempt_number" integer;
UPDATE "attempt" SET "attempt_number" = "n" WHERE "attempt_number" IS NULL;
CREATE UNIQUE INDEX "attempt_delivery_id_attempt_number_key" ON "attempt" USING btree ("delivery_id","attempt_number");
```

`n` and its own unique index (`attempt_delivery_id_n_key`) are untouched, and no application code reads or writes `attempt_number` yet — this migration is safe to run against a fresh database or an already-populated one (every row existing at migration time gets backfilled by the `UPDATE`), and old application code keeps working unmodified because it only ever touches `n`.

Be precise about what that leaves behind: from the moment 0006 lands until the dual-write deploy in step 2 goes out, every `attempt` row the worker writes has `attempt_number IS NULL`, because the insert path still only sets `n`. That is expected and harmless — the column is nullable, nothing reads it, and Postgres's default `NULLS DISTINCT` means the new unique index tolerates any number of NULL rows rather than colliding on them — but it is exactly the gap step 3 has to sweep up. `attempt_number` is not trustworthy as a source of truth until that sweep has run and returned zero.

What's intentionally **not** in this change, by design (steps 2–4 above), because bundling them here would be exactly the "add + drop in one revision" pattern this checklist forbids:

- A follow-up deploy adds dual-write (`insert` sets both `n` and `attempt_number`) and dual-read (prefer `attempt_number`, fall back to `n`) in `packages/db/src/repositories/deliveries.ts`.
- Once that deploy is live on every replica, the step 3 sweep (`UPDATE "attempt" SET "attempt_number" = "n" WHERE "attempt_number" IS NULL`) fills the rows written in the gap, and its residual count is checked to be zero. Waiting alone does not do this — those rows never get rewritten.
- Only then does a **contract** migration drop `n` and `attempt_delivery_id_n_key`, with the dual-write/fallback code deleted in the same deploy that ships it (the drop only ever lands after the code that depended on the old column is already gone). Making `attempt_number` `NOT NULL` belongs to that same contract revision, not to 0006.

## What this doesn't change

Compose's topology (ADR 0008) is unchanged: `migrate` still runs to completion before `api`/`worker` start on both a fresh database (all migrations apply in order) and an upgraded one (only the new migration(s) apply). This checklist is about how each individual migration is shaped, not about the deploy ordering that runs it.
