## Anti-Patterns Verdict

**Does this look AI-generated? No, and not narrowly.**

**LLM assessment.** No hero-metric tile, no identical card grid, no gradient, no modal, no illustration, no pill
badge, no 8px Bootstrap radius. The status lamp is an invented-but-earned component that carries state four
independent ways, and the domain vocabulary is enforced down to the empty-state copy. Squint at the page and it
reads "instrument", not "admin template". A Linear or Grafana user would trust it on sight.

The failure mode here is the inverse of slop and worth naming directly: **a central part of the design system
is asserted in comments but not perceptible on screen.** Measured in the running app, light theme:

| Edge                                   | Contrast vs `--face` |
| -------------------------------------- | -------------------- |
| `--lip-light` (the "raised" highlight) | **1.021**            |
| `--lip-shade` (the "recessed" shade)   | 1.277                |
| `--score` (the plain 1px border)       | 1.402                |

The lip highlight resolves to `rgb(255,255,255)` over a `rgb(251,253,253)` face: a four-point step, invisible.
In dark it measures 1.222 and does read. So the machining ships in dark and not in the light theme DESIGN.md
declares the default. What actually renders in light is a disciplined flat graphite UI with 2px radii. That is
a good thing to be; it is not the thing §4 claims.

**Deterministic scan.** `detect.mjs` over 31 files: exit 2, **6 findings, 0 bans, 6 warns**.

- 2x `pure-black-white` at `styles.css:9` — **false positives at the matched line, but they point at a real
  violation this critique originally cleared in error.** Both matches are the same comment line asserting the rule
  is followed, and a grep does confirm zero `#fff`/`#000` literals and zero `rgb()`/`hsl()` calls. That grep is
  the wrong instrument. The Anodized Grey Rule bans untinted neutrals, not a hex notation, and `--lip-light` is
  `oklch(100% 0 0 / 0.9)` with `--lip-shade` at `oklch(0% 0 0 / 0.35)`: pure white and pure black at chroma 0,
  defined three lines below the comment that denies they exist. Assessment A caught this and named it; this
  synthesis dropped it in favour of the detector's hex-literal grep, which is precisely the failure mode of
  letting a deterministic scan overrule a design review. The values were also printed in this run's own contrast
  measurements, so the evidence was in hand at the time of writing. Tracked as issue #70.
- 1x `em-dash` at `EndpointsTab.tsx:76` — **false positive**, inside a JSX comment, never rendered.
- 1x `em-dash` at `DeliveryDetail.tsx:19` — renders, but as a tabular placeholder in
  `<span role="img" aria-label="No status code recorded">`. A glyph in a data column, not punctuation. Correct as-is.
- 1x `layout-animation` at `styles.css:763` (`transition: left 120ms`) — contested, negligible on a 24px plunger,
  already reasoned about in-file.
- 1x `generic-sans-font` at `styles.css:108` — **the one finding worth carrying forward.** A system stack with no
  chosen typeface, in a stylesheet that tokenizes radii to 2px/3px and specifies zero-blur hairline lips. The
  product register explicitly permits system fonts, so this is a question rather than a defect: a Faceplate that
  specifies everything else and defaults its typeface is inconsistent with its own ambition.

16 grep cross-checks came back clean: no radius above 3px, no outer blurred shadow, no thick side border, no
`background-clip: text`, no `backdrop-filter`, no undefined token, no Both-Themes asymmetry, no bouncy easing,
no untreated native checkbox, no interactive element without a focus style. The deterministic surface is in
unusually good shape.

**One detector-adjacent correction.** Assessment B reported "0 icon imports of any kind — there is no icon
library in the dashboard at all". That is wrong: **18 files import `lucide-react`**, and the glyphs render. Its
grep was silently broken by zsh glob expansion on `--include=*.tsx`. The One Icon Family rule holds.

**Visual overlays.** None. The `detect.js` overlay was never injected, so there is nothing highlighted in your
browser. Both sub-agents hit a chrome-devtools MCP profile lock; it turned out to be an orphaned Chrome from a
previous session holding `~/.cache/chrome-devtools-mcp/chrome-profile` with `--remote-debugging-pipe`. After
closing it, live inspection succeeded in the parent, which is where all the measured evidence above and the
first priority issue below come from.

## Overall Impression

The drill-down is the best thing here and it genuinely works: a directory row carrying a failure count lands
you on `?filter=failed`, expand a Broadcast, expand a Delivery, read the numbered Attempt timeline with the raw
error. One continuous path, zero modals, every step addressable in the URL. That is PRODUCT.md's hardest
requirement, delivered.

The single biggest opportunity is that **the screen at the end of that path lies about what it found.** Filter
stripe-prod to failures only and you get a wall of green check lamps reading "3/4 succeeded". The filter and
the lamp are using two different definitions of the word failure, and the operator is looking at the one screen
whose entire job is to be trusted during an incident.

Everything else is craft work on a foundation that is already good.

## What's Working

1. **The lamp is load-bearing, not a restyled badge.** `StatusBadge.tsx:97-113` separates the two most confusable
   Delivery states by form _and_ glyph _and_ label before color is involved: `pending` is a hollow clock,
   `in_progress` a lit ring. Strip color entirely and every state survives. PRODUCT.md's one hard accessibility
   requirement is met structurally rather than by annotation.
2. **The copy is operator-grade without exception.** `'Headers must be valid JSON (e.g. {"x-api-key": "secret"})'`
   (`EndpointForm.tsx:48`) names the constraint and shows the shape. The auto-disable notice explains the
   mechanism, its irreversibility, and the remedy in three clauses, and declines to print a threshold it cannot
   verify for the deployment. No reassurance, no exclamations, no em dashes in rendered prose.
3. **State lives in the URL, so a link is a shareable diagnosis.** Channel, tab, expanded Broadcast, and filter
   are all addressable, and toggling a Broadcast preserves the filter rather than dropping back to the
   unfiltered list. For a team pasting links at each other mid-incident this is the highest-leverage decision in
   the app, which is exactly why the two ways it gets undercut (below) matter.

## Priority Issues

### [P1] The Activity filter and the fan-out lamp disagree about what a failure is

- **What**: `fanoutHasFailure` returns true when `failed > 0 || deadLettered > 0` (`lib/activityFilter.ts:29`).
  `BroadcastFanoutBadge` only lights Cut when `deadLettered > 0`, and everything else falls through to
  Live / lit / check labelled `${succeeded}/${total} succeeded` (`components/StatusBadge.tsx:138-155`). A Broadcast
  with `failed: 1, deadLettered: 0` therefore _passes the failures filter_ and _renders as a green success_.
  Measured live on `stripe-prod` at `?filter=failed`: the first six rows all carry
  `class="lamp lamp-live lamp-lit"` at `oklch(52% 0.14 152)` reading "3/4 SUCCEEDED".
- **Why it matters**: The operator explicitly asked to see only what is broken and got a screen of green check
  lamps. It breaks PRODUCT.md principle 1 (health before detail) and principle 4 (failure is information), and
  it puts Lamp Live on something that is not `succeeded`, which DESIGN.md's own lamp table reserves it for. The
  in-file reasoning is sound in isolation ("a merely failed Delivery still has retries left") but it was never
  reconciled with the filter that ships beside it. This is the one place the instrument is not telling the truth.
- **Fix**: Give the badge a third branch. When `failed > 0 && deadLettered === 0`, render **neutral / lit** (work
  still outstanding, retries pending) with a label that names the outstanding count instead of making the
  operator subtract: `1 failing, 3/4 succeeded`. Reserve Live / lit for `succeeded === total`. Reserve Cut for
  `deadLettered > 0`, unchanged.
- **Suggested command**: `/impeccable harden`

### [P1] Every trailing row column is ragged, including the directory health lamp

- **What**: `.row-channel` is `minmax(var(--status-lamp-column), auto) auto 1fr auto auto` (`styles.css:974`) and
  each `.row` is its own grid container, so only track 1 is pinned. Measured across the seven live directory
  rows, the health lamp's left edge spans **901px to 1042px: a 141px spread**, and the widest label
  (`7 failing (24h) · 1 auto-disabled`) is the one furthest out of line.
- **Why it matters**: DESIGN.md §Rows justifies the entire row grid as "a lamp lands at the same x... so the eye
  can run the column without reading", and PRODUCT.md principle 3 is "rows should be comparable down a column".
  The one lamp that answers the directory's whole reason for existing has the ragged edge, and it is worst on
  the rows that are actually broken. This is the "density without ranking" anti-reference resurfacing at the
  column level.
- **Fix**: Move the grid to the `<ul>` with a shared `grid-template-columns` and rows as `display: contents` or
  subgrid, so tracks size across the list rather than per row. Pin the health track to a second constant token
  (`--health-lamp-column`) beside `--status-lamp-column`. Same fix for `.row-activity` (`styles.css:977`) and the
  Endpoints reuse of `.row-channel` (`EndpointsTab.tsx:163`).
- **Suggested command**: `/impeccable layout`

### [P1] Every confirm and edit flow destroys keyboard focus, and the Endpoint row has no affordance

- **What**: Revoke swaps the token row for a confirm region (`ChannelTokensPanel.tsx:107`), Delete Channel swaps
  the button for one (`ChannelDangerZonePanel.tsx:50`), and clicking an Endpoint row replaces it with the edit
  form (`EndpointsTab.tsx:144-165`). In all three the trigger unmounts, so focus falls to `<body>`, nothing is
  announced, and `Escape` cancels none of them. The Endpoint row is additionally the only expandable row family
  with no disclosure chevron and no `aria-expanded` (2 hits exist, both elsewhere), and it is _replaced_ rather
  than expanded, so the lamp and name of the Endpoint being edited vanish.
- **Why it matters**: A keyboard operator activates "Revoke", hears nothing, and must tab from the top of the
  document to reach a destructive "Confirm revoke" they cannot confirm exists. DESIGN.md §4 specifies exactly
  this focus contract for overlays, then leaves inline expansion, the pattern that replaced overlays here,
  without it. And DESIGN.md §5 opens with "Every control states its affordance at rest": an operator clicking to
  read a truncated Endpoint URL is dumped into an edit form instead.
- **Fix**: On each swap move focus to the region's first control via a ref; give each region `role="group"` with
  an `aria-label` naming its target; bind `Escape` to the same handler Cancel calls. Add `aria-expanded` and a
  `ChevronRight`/`ChevronDown` to the Endpoint row, and render the form in a well _below_ the retained row the
  way `BroadcastDetailPanel` does. Guard the swap when the open form is dirty.
- **Suggested command**: `/impeccable harden`

### [P2] The URL is this app's best idea, and the UI undercuts it twice

- **What**: Two separate gaps found live. (a) Channel directory rows are `<button className="row row-channel">`
  with programmatic navigation, not `<a>` (verified in the DOM: the page contains exactly one anchor, `/`). So
  cmd-click, middle-click, "open in new tab", "copy link address", and the hover URL preview all do nothing, and
  a screen reader announces "button" with no hint it navigates. (b) Routes are keyed by UUID
  (`/channels/69d737fb-…/activity`), and a hand-written `/channels/stripe-prod` renders the raw API string
  **`channelId must be a UUID`** as a `role="alert"` rather than the not-found panel, even though slug lookup
  exists server-side (issue #40, closed).
- **Why it matters**: The app went to real trouble to make every view addressable, then made the addresses
  unusable by hand and un-openable in a second tab. An operator triaging three Channels at once cannot fan them
  out into tabs, which is the single most natural thing to do during an incident.
- **Fix**: Render the row as a `<Link>` styled with the existing `.row` classes (DESIGN.md §Controls already
  requires geometry to live on classes precisely so a `Link` and a `button` are indistinguishable). Accept the
  slug in the route and resolve it to an id, or redirect slug to UUID. Map unparseable route params to
  `NotFoundPanel` instead of surfacing `err.message`.
- **Suggested command**: `/impeccable clarify`

### [P2] The machined lip does not ship in the light theme, and nested wells share one ground

- **What**: Measured above: the raised highlight is 1.021 contrast against its own surface in light, versus 1.277
  for the recess and 1.402 for the plain border. Raised and recessed are not symmetrical in practice, so the
  Lip Direction Rule reads in one direction only. Separately, at the terminal point of the whole product, the
  expanded `.well-broadcast` and the `.payload` nested inside it both compute to
  `oklch(0.94 0.006 195)` — the identical background, separated only by a 1px border and an indent. The Inward
  Depth Rule promises "darker, tighter, inset" and there is no token below `--well` to go darker into.
- **Why it matters**: Not an accessibility problem and not visible as a bug. It is the gap between what
  DESIGN.md says the system is and what renders, which matters because that document is being cited as binding
  in code comments. Either the tokens should become perceptible or §4 should stop claiming they are.
- **Fix**: Either raise `--lip-light` in the light theme until the highlight clears roughly 1.10 contrast against
  `--face` and add a `--face-raised` a step above `--face` for controls, or accept the flat reading and rewrite
  §4 to describe what ships. Add a `--well-deep` token for second-level nesting.
- **Suggested command**: `/impeccable bolder`

## Persona Red Flags

**Alex (impatient power user)** — the primary persona for this surface.

- Cannot open a Channel in a new tab. Rows are buttons, so cmd-click does nothing and there is no link to copy.
- Zero keyboard shortcuts: no `j`/`k` down the row list, no `/` to filter, no `g`-then-key. For a surface
  explicitly benchmarked against Linear, the most visible omission. (#53)
- No bulk actions at all. A Broadcast dead-lettered to six Endpoints is six expansions and six separate Retry
  presses (`DeliveryDetail.tsx:140-148`). (#53)
- The Activity filter has exactly two options on the product's busiest list: no filter by Endpoint, status code,
  or time range. `Load more` is the only pagination.

**Sam (accessibility-dependent)**

- The tab strip has no programmatic active state: three plain `<button>`s in a `<nav>` with the active one marked
  by a CSS class only (`ChannelDetailPage.tsx:132-141`). No `aria-current`, no `role="tablist"`/`aria-selected`.
- Focus destroyed by all three confirm/edit swaps, with no `Escape` anywhere.
- `InlineLoadError` nests a `<button>` inside a `role="alert"` `<p>`, so "Retry" is announced as alert text, and
  with `retry: false` on a 5s poll it re-fires indefinitely.
- The green fan-out lamp is the one place color and label disagree, and a screen reader user gets only the
  label, which says "succeeded" about a Broadcast that did not fully succeed.
- Positive: color is never the sole carrier anywhere, skeletons carry `role="status"` with labels, and the theme
  toggle's `aria-label` names both state and consequence.

**Riley (deliberate stress tester)**

- Hand-types `/channels/stripe-prod` and gets `channelId must be a UUID` in red.
- Opens two Endpoint edit forms in sequence: the first form's unsaved changes vanish with no prompt.
- Types `My Channel!` into New Channel: the placeholder stating the kebab-case rule has already disappeared
  behind their own text, `required` is the only client guard, and the constraint surfaces only as a server error.
- Pastes a 400-character Endpoint URL: ellipsised with no `title` and no way to read it without entering edit mode.
- Refreshes mid-edit: `editingId` is local state and is the one expansion state in the app not in the URL.

**Nadia (fan-out owner, arriving because an integration reported a missing payload)** — derived from PRODUCT.md's
reactive job.

- Clicks a row reading "19 failing (24h)", lands on the filtered Activity view, and sees green check lamps. She
  now has to decide whether the filter is broken or the Channel is fine. Neither is true.
- The number she navigated on is not restated anywhere on Channel detail.
- The first plate on the page is the Ingest URL, which is configuration, not health. Her rows start below it.
- She reaches `HTTP 503` and needs to know whether the worker will retry. The `failed` vs `dead_lettered`
  distinction is documented only in ADR 0003 and expressed silently as the presence of the Retry control.

## Minor Observations

- `EndpointAutoDisabledNotice` renders in `.confirm-region` (`EndpointsTab.tsx:60`), but DESIGN.md defines
  `.advisory` for exactly this case. An informational notice looks identical to a destructive confirmation.
- Two filled `control-primary` sit on screen at once on the Endpoints tab, against "one per plate, never two".
  The comment at `EndpointsTab.tsx:72-77` reasons carefully against this for the Re-enable control, then the
  form does it anyway.
- The New Channel form is the only form in the app using placeholder-as-label
  (`ChannelDirectoryPage.tsx:77-94`), against DESIGN.md §Fields "Label ... always present". It also outranks the
  health list it sits above, which inverts PRODUCT.md principle 1 on the app's most-visited screen.
- The directory sorts unhealthy Channels first but does not rank them by severity: 7 failing, then 1 failing,
  then 19 failing.
- `NotFoundPanel` uses the neutral dashed `.empty-state` treatment rather than the inline Lamp Cut error
  treatment DESIGN.md §Loading/empty/error specifies.
- `--lamp-live` as 11px 600-weight text on `--face` measures near 4.3:1, just under AA. PRODUCT.md declines AA as
  a requirement, so advisory only, but a one-step darkening costs nothing.
- Every server error reaches the user unmodified via `err.message`; validation detail is formatted well
  (`lib/api.ts:45-64`) but an unhandled 500 renders whatever `statusText` happened to be.
- The 225ms skeleton delay (`styles.css:1220-1224`) is a genuinely thoughtful detail worth keeping.
- The directory leaves roughly 40% of the viewport empty below seven rows, while the health column it does draw
  is the ragged one.

## Questions to Consider

1. The fan-out lamp's rule ("only dead-lettered is red") and the filter's rule ("failed or dead-lettered is a
   failure") are each defensible alone. Which one is the product's actual definition of a failure, and what
   would change if you wrote it down once and made both read from it?
2. If the lip is invisible in the light default, is "The Faceplate" shipping, or is the real system "graphite,
   2px, one accent, lamps not pills" with the machining living only in CSS comments? Would committing to a
   perceptible lip make it true, or would admitting it is flat free you to spend that effort on the row grid?
3. The directory's health lamp is the highest-value glance in the product and it currently floats in an `auto`
   track. What if the directory stopped being a row list and became a real fixed-column table, the one place
   where "scanning beats reading" would justify table semantics?
4. Every recovery action is single-item. A Broadcast that dead-lettered to six Endpoints is six clicks. Given
   the fan-out is the unit of this product, what is the argument against "Retry all dead-lettered" on the
   Broadcast itself?
