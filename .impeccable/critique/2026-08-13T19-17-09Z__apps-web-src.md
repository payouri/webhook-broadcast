## Anti-Patterns Verdict

**Does this look AI-generated? No.** This is one of the more disciplined product surfaces I have reviewed against its own spec. There are no gradients, no shadows, no glassmorphism, no hero-metric tiles, no icon-and-heading card grids, no modals, no side-stripe borders, and no illustration anywhere. The palette is a real decision (warm hue-75 paper with a wine accent) rather than the category reflex of dark-blue-on-charcoal, and the code comments show the reasoning was deliberate rather than decorative. The `StatusBadge` outlined-versus-filled split so that `PENDING` and `IN PROGRESS` survive color removal is the kind of thing most teams write down and never build.

The failure mode here is not slop. It is **spec drift**: DESIGN.md describes a tighter, more ranked system than the CSS actually implements, and the gaps all point the same direction, toward flatness.

## Overall Impression

The instrument is honest and the vocabulary is exact. What it is not yet is *scannable*, which is the one thing PRODUCT.md says it exists to be.

The stated job is "confirm at a glance that Channels are healthy and nothing is dead-lettering." The Channel directory does that well: the health badge carries a count in its label, not a dot. But one click deeper, on the Activity list where the operator actually lives, the failure signal is rendered in `--ink-muted` grey at the far right of the row, in the same weight as the timestamp beside it. A Broadcast that dead-lettered looks exactly like a Broadcast that succeeded until you read the text. The whole design system was built to make state legible without reading, and then the busiest list in the product asks you to read.

The single biggest opportunity: give the Activity row the same status stamp every other row already has, and give the operator a way to filter to failures. Those two changes convert this from a browsable log into the diagnostic instrument the PRODUCT.md describes.

## What's Working

**The status vocabulary is genuinely excellent.** One component (`StatusBadge`) renders Channel enabled state, Endpoint auto-disable, and Delivery status through a single presentation, and `tone` and `form` are independent axes so the two most confusable states differ in fill as well as color. `ChannelHealthBadge` putting the count in the *label* ("3 failing (24h)") rather than in a color is exactly right, and it means a screen reader gets the number for free. PRODUCT.md made "status is never encoded in color alone" a hard requirement and this actually delivers it.

**Progressive disclosure with zero modals.** Channel to Broadcast to Delivery to Attempt is a continuous inline drill-down, each level recessed onto Surface Sunk and inset from its parent, with the expanded Broadcast encoded in the URL so a reload or a shared link lands on the same view. That is PRODUCT.md principle 5 ("one path from symptom to cause") built correctly, and it is rarer than it sounds.

**The copy holds its voice under pressure.** `'Headers must be valid JSON (e.g. {"x-api-key": "secret"})'`, "Any producer using wbt_abc… stops being accepted. This cannot be undone.", "No Broadcasts yet. Send a request to `POST /ingest/<slug>` with a Channel token." No reassurance, no apology, every message names the constraint. `CopyButton` even reports a *failed* copy rather than swallowing it, with a comment citing "failure is information."

## Priority Issues

### [P1] The Activity list hides the failure it exists to surface

**What**: `ChannelActivityTab.tsx:123` renders the fan-out result as `<span className="muted activity-fanout">`, so "2/3 succeeded, 1 dead-lettered" is Ink Muted grey, right-aligned, at 0.8rem. The Broadcast row has no status stamp at all, unlike the Channel row, the Endpoint row, and the Delivery row.

**Why it matters**: This is the screen where the routine check actually happens, and it is the one place a failure is not visible without reading. It breaks PRODUCT.md principle 1 ("health before detail") and principle 3 ("scanning beats reading") simultaneously. It also violates the design system's own logic: `--signal-cut` is quarantined to Delivery status, and a fan-out summary *is* aggregate Delivery status, so a stamp here is not just permitted, it is the intended use.

**Fix**: Give `.activity-row` a leading status stamp column using the existing `--status-stamp-column` variable, matching `.channel-row`. Render a `StatusBadge`: danger/filled when `deadLettered > 0` (label carrying the count, e.g. "1 dead-lettered"), neutral/outlined when `total === 0`, success/filled otherwise. Move the timestamp out of the leading position. Drop `.muted` from `.activity-fanout` and let the stamp carry the signal.

**Suggested command**: `/impeccable layout`

### [P1] Nothing connects "3 failing (24h)" to those three failures

**What**: The directory advertises a failure count per Channel. Clicking through lands on an unfiltered, newest-first Broadcast list paginated by "Load more". There is no filter by Delivery status, no search, no time range, and no way to jump to the failures. A dead-lettered Delivery from six hours ago on a busy Channel is an unknown number of "Load more" clicks away.

**Why it matters**: PRODUCT.md ranks "trace a specific failure from Channel to Broadcast to Delivery to the Attempt error string" as the second most frequent job and states that "a real failure takes one navigation path (not a search) to reach the underlying HTTP error." Today it takes a search, and the search tool does not exist. This is the finding that drags heuristic 7 to a 1.

**Fix**: Add a filter control above the Activity list, at minimum "All / Has failures". It maps cleanly onto the fan-out data already in `BroadcastListItem`. If the API cannot filter server-side yet, make the Channel health badge itself the entry point: a "3 failing (24h)" badge that navigates to a filtered Activity view is one navigation path, which is exactly what the principle asks for.

**Suggested command**: `/impeccable shape`

### [P1] The signature Delivery Row is not built to its own spec

**What**: DESIGN.md §5 defines the Delivery Row with a "fixed leading column: the status stamp, at a constant width so stamps align vertically down the list and the eye can run the column without reading." `.delivery-row` (`styles.css:507`) is `display: flex`, and `.status-badge` is `display: inline-flex` sized by its own label. `SUCCEEDED`, `FAILED`, `DEAD LETTERED`, `PENDING`, and `IN PROGRESS` are five different widths.

**Why it matters**: Computed from the CSS, every Endpoint name in a Delivery list starts at a different x position depending on that row's status. On a fan-out to eight Endpoints with mixed outcomes, the middle column is visibly ragged and the eye cannot run either column. `.channel-row` already solves this correctly with `minmax(var(--status-stamp-column), auto)` and a comment explaining exactly why. The signature component did not get the same treatment. `.attempt-row` has the same problem.

**Fix**: Convert `.delivery-row` to the same grid shape as `.channel-row`, reusing `--status-stamp-column` for the leading track. Do the same for `.attempt-row`, whose `#n` column should also be fixed-width. Separately, `DeliveryDetail.tsx:76` applies `.delivery-row-wrapper`, which has no rule in `styles.css`; either style it or remove it.

**Suggested command**: `/impeccable layout`

### [P1] The type scale is not a scale

**What**: `styles.css` contains seven font sizes: 0.6875, 0.8, 0.85, 0.9, 0.95, 1, 1.25rem. Only two of them (1rem, 1.25rem) match a role declared in DESIGN.md's typography tokens, and none of the tokens exist as CSS custom properties. The four middle values sit at ratios of roughly 1.06 apart. Worse, two headings have no `font-size` rule at all and fall through to UA defaults: the app header's `<h1>webhook-broadcast</h1>` (`App.tsx:58`) renders at 2em (32px), and the Channel slug `<h2>` in `.channel-header` (`ChannelDetailPage.tsx:113`) renders at 1.5em (24px). DESIGN.md puts both at the Headline role, 1.25rem (20px), "one per screen."

**Why it matters**: Computed from the CSS. The loudest element on every screen is the product name, which the operator already knows, at 60% larger than spec. Meanwhile four content sizes that differ by 1 to 2 pixels read as noise, not rank, so the actual hierarchy has to be carried by position alone. DESIGN.md asks for a "tight 1.15 to 1.25 ratio, so that hierarchy reads as rank rather than as drama." What shipped is neither ratio nor rank.

**Fix**: Promote the five DESIGN.md roles to custom properties (`--type-stamp: 0.6875rem`, `--type-label: 0.8125rem`, `--type-data: 0.8125rem`, `--type-body: 0.9375rem`, `--type-title: 1rem`, `--type-headline: 1.25rem`) and replace all seven literals with them. Add explicit `font-size` to the header `h1` and `.channel-header h2`. Placeholder text also has no rule and inherits the browser's untinted grey, which breaks the Warm Grey Rule; add `::placeholder { color: var(--ink-muted); }`.

**Suggested command**: `/impeccable typeset`

### [P2] A 720px cap on everything, and no responsive rules at all

**What**: `.app-main` sets `max-width: 720px` with no exceptions, and `styles.css` contains zero `@media` queries. DESIGN.md §5 Navigation says the opposite: "tabular regions (Delivery rows, Attempt rows, Endpoint rows) may extend to the full viewport width; the cap must not starve data of horizontal room," and "below 640px, row grids collapse to stacked lines and metadata wraps rather than truncating."

**Why it matters**: Inside 720px, minus 48px of `.app-main` padding and 40px of panel padding, a Delivery row has about 632px to hold a status stamp, a monospace Endpoint URL, and `HTTP 503 · 4213ms`. `.delivery-endpoint` truncates with `text-overflow: ellipsis`, so the operator reading a fan-out sees a column of URLs cut off at roughly the same place, which is the least useful place to cut a URL. The `.channel-row` five-column grid has no collapse rule, so a narrow window crushes it rather than stacking it. PRODUCT.md says desktop, which keeps this at P2 rather than P1, but "desktop" includes a half-width window beside an editor, which is precisely how this tool is described as being used.

**Fix**: Keep the 720px cap for prose and form panels; let the Activity, Endpoints, Delivery, and Attempt regions run wider (a `--content-max` and a `--data-max`, or a wider `.app-main` with a capped prose class). Add the sub-640px collapse DESIGN.md already specifies.

**Suggested command**: `/impeccable adapt`

## Persona Red Flags

**Alex (Impatient Power User)**: There is not one keyboard shortcut in the codebase; `grep` for `onKeyDown` across `apps/web/src` returns nothing. No `/` to search, no `j`/`k` to move down the Activity list, no Esc to collapse an expanded Broadcast or to back out of a confirm region. No bulk actions: on a Channel where a downstream service was down for an hour, every dead-lettered Delivery must be expanded and retried one at a time, each retry a separate click into a separate expansion. No way to filter, so finding the failures means "Load more" until they appear. Alex will do this twice and then go back to `psql`, which is the exact outcome PRODUCT.md's purpose statement is written to prevent.

**Sam (Accessibility-Dependent User)**: Mostly well served, which is worth saying, and the gaps are specific. Focus rings are declared on every interactive class including the ones that render as anchors, status never relies on color alone, and every control has a text label. Three real failures: (1) `ChannelSettingsForm.tsx:79` puts `role="alert"` on the slug-rename warning, which re-renders on every keystroke in the slug field, so a screen reader re-announces the full two-sentence warning character by character while typing. That should be `role="status"` on a debounced value, or plain text with no live region. (2) The "unauthenticated ingest" tag at `ChannelDetailPage.tsx:114` carries its entire explanation in a `title` attribute, which is invisible to keyboard and touch users and inconsistently announced by screen readers. That is a security-relevant fact delivered hover-only. (3) Heading structure: the app `<h1>` is the product name on every route, so the page itself has no `h1`, and the Channel slug `<h2>` sits at the same level as the panel headings beneath it, flattening the outline for anyone navigating by heading.

**Morgan (Operator Under Pressure, derived from PRODUCT.md)**: Arrives at 4pm because an integration says it never got its payload. Opens the directory, sees "2 failing (24h)" on the right Channel, clicks in, and lands on an unfiltered Activity list where the failed Broadcast is visually indistinguishable from the healthy ones until read. Finds it, expands, finds the dead-lettered Delivery, expands, reads `HTTP 503` and an error string. That part works well. Then hits the wall: the Endpoint shows "Auto-disabled since 8/13/2026, 2:04:11 PM" and nothing anywhere in the interface explains what auto-disables an Endpoint, after how many failures, or how to re-enable it. PRODUCT.md lists "re-enable an auto-disabled Endpoint" as job 4, and the only path is to click the Endpoint row into edit mode and tick a checkbox labeled "Enabled", which is discoverable only by guessing. Under pressure, that is the moment Morgan opens the README.

## Minor Observations

- **Nested panels, an explicit DESIGN.md ban.** `EndpointsTab.tsx:64` renders `<li key={endpoint.id} className="card">` inside `<section className="card">`. "Panels never nest. A panel inside a panel is always wrong." The editing state should be an inset Surface Sunk region, the same treatment `.broadcast-detail` and `.confirm-region` already use.
- **One panel is outside the freshness system.** Every other data surface uses TanStack Query with `freshnessRefetchInterval`, but `ChannelTokensPanel.tsx` uses a manual `useCallback` + `useEffect` fetch. It never refreshes on a poll, and it calls `api.getChannel(channelId)` a second time for data the parent `ChannelDetailPage` already has in the `["channel", channelId]` cache.
- **Destructive confirms look like routine saves.** "Confirm revoke" and "Confirm delete" are bare `<button>`, which means Patch Plum, identical to "Save changes" and "Mint new token". The One Voice Rule justifies plum for operator intent, but nothing distinguishes irreversible intent from routine intent at the moment it matters most. Consider Signal Cut text on a ghost shell, or at minimum reversing which of the pair gets the fill.
- **Two primary buttons in one panel.** DESIGN.md: "One per panel, never two." The Ingest tokens panel has "Mint new token" plus a plum "Confirm revoke" whenever a confirm region is open.
- **`.channel-row` is doing two jobs.** Endpoints reuse the Channel row grid, but the column meanings differ, and `.channel-slug` (an `auto` track that does not truncate) receives `endpoint.name ?? endpoint.url`. An unnamed Endpoint puts a full URL in a non-truncating column and will blow out the grid.
- **Timestamps are absolute only.** `new Date(...).toLocaleString()` yields "8/13/2026, 2:04:11 PM" in the Activity, Attempt, token, and auto-disable rows. For an ops surface the convention is relative ("2m ago") with the absolute value on hover, both because it is shorter and because "how long ago" is the actual question.
- **The polling is invisible.** Data refreshes every 5s but nothing on screen says so or shows when it last succeeded. A silently failing poll is indistinguishable from a quiet system, which is the one ambiguity an instrument should never have.
- **`.link-button` has a transition on `opacity` but no rule ever changes it.** The header home link has no hover response at all.
- **Four real em dashes in copy** per the detector, at `BroadcastDetailPanel.tsx:62` (a code comment), `ChannelTokensPanel.tsx:72` and `:130`, `IngestUrlPanel.tsx:30`. The fifth hit is a false positive.

## Questions to Consider

- The design system spends its precision on making a *single* status legible. What would it take to make a *list* of statuses legible, so the operator ranks twenty rows without reading any of them?
- If the Channel health badge already knows there are three failures, why is it a label rather than a link?
- What is the one screen an operator should be able to leave open all day? Right now the answer is the directory, and it refreshes silently. Should it be telling them it is alive?
- DESIGN.md is unusually well written and the code comments cite it by section. What would keep the CSS from drifting from it again: tokens as custom properties, or a check that fails the build?
